## 📋 1. Help Requests Data Model

### Table Structure

**Firebase Collection:** `help_requests`

```typescript
{
  // Identity
  id: string,                    // Auto-generated by Firebase
  caller_id: string,             // Phone number (e.g., "+1234567890")
  caller_name: string,           // Customer name
  call_session_id: string,       // Links to full conversation
  
  // Content
  question: string,              // What the customer asked
  context: string,               // Conversation history/context
  
  // State Management
  status: "pending" | "in_progress" | "resolved" | "timeout",
  priority: "low" | "medium" | "high",
  
  // Timestamps
  created_at: timestamp,         // When request was created
  updated_at: timestamp,         // Last modification
  timeout_at: timestamp,         // created_at + 30 minutes
  resolved_at: timestamp | null, // When supervisor responded
  
  // Resolution
  supervisor_response: string | null,
  supervisor_id: string | null
}
```

### Design Rationale

**Why Firebase Firestore?**
- Real-time listeners for instant dashboard updates
- Scales automatically (no manual sharding)
- Simple setup, no server management
- Generous free tier (suitable for MVP)
- Built-in security rules

**Why these specific fields?**
- `call_session_id`: Allows linking to full conversation for context
- `timeout_at`: Pre-calculated to avoid timestamp arithmetic in queries
- `status` enum: Enforces valid states, enables efficient filtering
- `priority`: Allows sorting by urgency in dashboard
- `context`: Helps supervisor understand full situation

### Indexes

```typescript
// Required indexes for performance
- status (for filtering pending vs resolved)
- created_at (for sorting by time)
- timeout_at (for background job efficiency)
- composite: (status + created_at) for dashboard queries
```

### Relationships

```
help_requests → knowledge_base
  After resolution, answer is added to KB
  Links via request_id in KB entry metadata

help_requests → call_sessions
  Foreign key: call_session_id
  Provides full conversation history

help_requests → supervisors (future)
  Foreign key: supervisor_id
  Track performance metrics
```

## 📚 2. Knowledge Base Structure

### Dual-Store Design

**Firebase Collection:** `knowledge_base` (source of truth)
```typescript
{
  id: string,
  question: string,              // Original question
  question_normalized: string,   // Lowercase, no punctuation
  answer: string,
  confidence: number,            // 0.0 - 1.0
  category: string,              // "hours", "pricing", "services"
  source: "initial_prompt" | "supervisor_answer" | "manual_entry",
  usage_count: number,
  created_at: timestamp,
  last_used_at: timestamp
}
```

**Vector Store:** ChromaDB (for semantic search)
```typescript
{
  id: string,                    // Same as Firebase
  embeddings: float[768],        // OpenAI text-embedding-3-small
  metadata: {
    question: string,
    answer: string,
    category: string,
    confidence: number
  }
}
```

### Update Flow

```
1. Supervisor resolves request
   ↓
2. Backend creates KB entry in Firebase
   ↓
3. Generate embeddings (OpenAI API)
   ↓
4. Upsert to vector store (ChromaDB)
   ↓
5. Next query uses semantic search
```

### Duplicate Prevention

```python
async def add_entry(question, answer):
    # 1. Normalize question
    normalized = normalize(question)
    
    # 2. Check exact match
    existing = db.where("question_normalized", "==", normalized).get()
    if existing:
        # Update usage count instead
        existing.usage_count += 1
        return
    
    # 3. Check semantic similarity
    similar = vector_store.search(question, threshold=0.95)
    if similar:
        # Update existing entry with new answer
        update_entry(similar[0].id, answer)
        return
    
    # 4. Add new entry
    create_entry(question, answer)
```

### Design Rationale

**Why dual storage (Firebase + ChromaDB)?**
- **Firebase:** CRUD operations, real-time sync, backup
- **ChromaDB:** Fast semantic search, handles synonyms
- Best of both worlds: structured data + vector search

**Why normalize questions?**
- Catches exact duplicates despite formatting
- Improves cache hit rate
- Faster fallback search if vector store fails

**Why track usage_count?**
- Identify most common questions
- Prioritize KB entries for optimization
- Analytics for business insights

## ⏰ 3. Supervisor Timeout Handling

### Strategy: Graceful Degradation

**Implementation:** Background job in `backend/lifecycle.py`

```python
# Runs every 5 minutes
async def check_timeouts():
    now = datetime.now()
    
    # Find timed-out requests
    timed_out = db.collection("help_requests") \
        .where("timeout_at", "<", now) \
        .where("status", "in", ["pending", "in_progress"]) \
        .stream()
    
    for request in timed_out:
        # Mark as timeout
        request.update({"status": "timeout"})
        
        # Notify admin
        await notify_admin(request)
        
        # Add to follow-up queue
        await add_to_manual_queue(request)
```

### Timeout Flow

**Scenario 1: Pending timeout (30 min)**
```
PENDING (created) → 30 min passes → TIMEOUT
  ↓
1. Mark request as timeout
2. Send alert to admin team
3. Add to manual follow-up queue
4. Customer gets: "We'll call you back within 1 hour"
```

**Scenario 2: In-progress timeout (30 min from start)**
```
IN_PROGRESS → 30 min passes → TIMEOUT
  ↓
1. Same as above
2. Also notify the assigned supervisor (reminder)
3. Track as "supervisor timeout" metric
```

### Prevention Measures

**Dashboard Features:**
- **Time remaining** shown on each card
- **Color coding**: Green (20+ min), Yellow (10-20 min), Red (<10 min)
- **Email alert** at 25 minutes
- **Priority sorting** (high priority + oldest first)
- **Mobile notifications** (future enhancement)

### Recovery Process

```python
# Supervisor can manually resolve timed-out requests
async def resolve_timeout(request_id, response):
    request = db.collection("help_requests").document(request_id).get()
    
    if request.status != "timeout":
        raise InvalidTransitionError()
    
    # Allow resolution even after timeout
    await update_request(request_id, {
        "status": "resolved",
        "supervisor_response": response,
        "resolved_at": datetime.now()
    })
    
    # Still update KB and notify customer
    await notify_customer(request)
    await update_knowledge_base(request)
```

### Metrics

Track timeout performance:
```python
metrics = {
    "timeout_rate": timed_out / total_requests,
    "avg_resolution_time": ...,
    "timeout_by_priority": {...},
    "timeout_by_supervisor": {...}
}
```

**Alerts:**
- Timeout rate > 20% → Warning
- Timeout rate > 40% → Critical (need more supervisors)

### Design Rationale

**Why 30 minutes?**
- Balance between customer patience and supervisor workload
- Long enough for complex research
- Short enough to maintain customer satisfaction
- Configurable via environment variable

**Why background job vs real-time triggers?**
- More reliable than database triggers
- Easy to test and monitor
- Can batch process multiple timeouts
- Doesn't impact request creation performance

**Why allow resolution after timeout?**
- Customer still wants the answer
- Better than leaving them hanging
- Can mark as "late resolution" for metrics

## 📈 4. Scaling Strategy (10/day → 1000/day)

### Current Architecture (10-100/day)

**Characteristics:**
- Direct API calls (no queue)
- Single database instance
- In-memory caching
- Synchronous processing

**Performance:**
```
- Request creation: ~100ms
- KB lookup: ~50ms (with cache)
- Vector search: ~200ms
- Dashboard load: <2s
```

**Cost:** ~$5-20/month

**Bottlenecks:** None at this scale

### Phase 1: 100-500/day

**Changes needed:**

1. **Add Redis Cache**
```python
# Cache KB lookups (hot entries)
@cache.memoize(timeout=300)
async def search_kb(question):
    return await kb_service.search(question)
```

2. **Database Connection Pooling**
```python
# Reuse connections
firebase_pool = ConnectionPool(
    min_size=2,
    max_size=10
)
```

3. **API Rate Limiting**
```python
# Prevent abuse
@limiter.limit("100/minute")
async def create_request():
    ...
```

4. **Horizontal Scaling**
```bash
# Run multiple backend instances
backend-1, backend-2, backend-3
Load balancer (Nginx)
```

**Cost:** ~$100/month

### Phase 2: 500-1000/day

**Changes needed:**

1. **Message Queue (RabbitMQ/SQS)**
```python
# Decouple agent → backend
await queue.publish("help_request", request_data)

# Worker processes queue
async def process_help_request(message):
    await save_to_db(message)
    await notify_dashboard(message)
```

2. **Worker Pool**
```python
# Background processing
workers = [
    timeout_checker,
    notification_sender,
    kb_updater,
    analytics_processor
]
```

3. **Database Read Replicas**
```
Write: primary instance
Read: replica-1, replica-2, replica-3
```

4. **Vector Database Upgrade**
```
ChromaDB (local) → Pinecone (managed)
  - Handles billions of vectors
  - Distributed search
  - Auto-scaling
```

**Cost:** ~$300/month

### Phase 3: 1000+/day

**Changes needed:**

1. **Kubernetes Orchestration**
```yaml
# Auto-scaling
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
spec:
  minReplicas: 3
  maxReplicas: 20
  targetCPUUtilizationPercentage: 70
```

2. **Distributed Caching**
```python
# Redis Cluster
cache = RedisCluster(
    nodes=["cache-1", "cache-2", "cache-3"]
)
```

3. **Analytics Pipeline**
```
Data → Kafka → Spark → BigQuery
  - Real-time metrics
  - Historical analysis
  - ML training data
```

4. **Frontend Upgrade**
```
Streamlit → React SPA
  - Better performance
  - Progressive loading
  - Offline support
```

**Cost:** ~$1000+/month (mostly infrastructure)

### Bottleneck Analysis

**Current bottlenecks by component:**

| Component | Current | At 1000/day | Solution |
|-----------|---------|-------------|----------|
| **Vector Search** | 50ms | Still 50ms | ✅ Scales well |
| **Firebase Writes** | 100ms | 100ms | ✅ Scales well |
| **LLM Calls** | 500ms | 500ms | Cache common responses |
| **Dashboard** | Streamlit | Slow | Upgrade to React |
| **Background Jobs** | Single thread | Bottleneck | Worker pool |

### Scaling Decisions

**Why not scale prematurely?**
- Current architecture handles 100/day easily
- Over-engineering wastes time and money
- Can upgrade incrementally
- Firebase + LiveKit Cloud scale automatically

**When to scale?**
- Response time > 1s (95th percentile)
- Error rate > 2%
- Timeout rate > 15%
- Cost becomes prohibitive

**How to scale cost-effectively?**
- Cache aggressively (Redis)
- Batch operations (notifications, analytics)
- Use cheaper models where possible (GPT-3.5 for simple queries)
- Reserved instances for predictable load

## 🏗️ 5. Modularization Architecture

### Design Principle: Separation of Concerns

Each module has a **single, clear responsibility** and **well-defined boundaries**.

### Agent Module

**Responsibility:** Voice interaction and escalation logic

```
agent/
├── agent.py              # LiveKit agent, handles voice I/O
├── knowledge.py          # KnowledgeBaseService (search, cache)
├── vector_store.py       # VectorStore (embeddings, semantic search)
├── tools.py              # request_help() function
├── prompt.py             # System prompts, greeting templates
└── tests/                # Unit tests for each module
```

**Key classes:**
- `SalonReceptionist`: Main agent class
- `KnowledgeBaseService`: KB search with semantic search
- `VectorStore`: Embeddings and similarity search
- `HelpRequestService` (in tools.py): Creates help requests

**Dependencies:**
- LiveKit SDK
- OpenAI client
- Firebase client
- ChromaDB

**Why separate?**
- Can test agent logic without LiveKit infrastructure
- Can swap voice providers (LiveKit → Twilio Voice)
- Can run in console mode for development

### Backend Module

**Responsibility:** API layer and business logic

```
backend/
├── main.py               # FastAPI app, routes
├── services.py           # Business logic layer
│   ├── HelpRequestService
│   ├── KnowledgeBaseService
│   └── NotificationService
├── models.py             # Pydantic models (validation)
├── database.py           # FirebaseClient (singleton)
├── lifecycle.py          # Background jobs (timeout checks)
├── error_handling.py     # Retry logic, circuit breakers
└── tests/                # Integration tests
```

**Key classes:**
- `HelpRequestService`: CRUD for help requests
- `KnowledgeBaseService`: KB management
- `NotificationService`: Customer notifications
- `FirebaseClient`: Database connection (singleton)

**API Design:**
```python
# RESTful endpoints
POST   /requests          # Create (from agent)
GET    /requests          # List (for dashboard)
PATCH  /requests/{id}     # Update (supervisor response)

GET    /knowledge_base    # List entries
POST   /knowledge_base    # Add entry
```

**Why separate from agent?**
- Agent and dashboard both use same API
- Can scale backend independently
- Can add more clients (mobile app, CLI)
- Clear separation: voice logic vs business logic

### Frontend Module

**Responsibility:** Supervisor interface

```
frontend/
├── dashboard.py          # Streamlit app (all-in-one)
└── README.md             # Setup instructions
```

**Why Streamlit?**
- All Python (no JavaScript needed)
- 300 lines vs 1000+ for React
- Perfect for internal dashboards
- Real-time updates built-in

**Future upgrade path:**
```
Streamlit → React
  When: >1000/day or need mobile app
  Why: Better performance, more control
  Cost: 3-4x more development time
```

### Communication Between Modules

**Pattern: REST API (Loose Coupling)**

```
Agent → HTTP → Backend ← HTTP ← Dashboard
             ↓
          Firebase
             ↑
          (Real-time)
             ↓
          Dashboard
```

**Why REST over RPC?**
- Language agnostic (could rewrite modules in different languages)
- Easy to debug (curl, Postman)
- Standard caching (HTTP headers)
- Load balancing straightforward
